# api-factory-mongo Usage Guide

This document explains how a frontend developer, API client, or LLM agent should consume the APIs generated by this service.

## What This Service Does

`api-factory-mongo` does not expose one fixed business API. Instead, it creates temporary Mongo-backed CRUD APIs from a schema definition.

Typical flow:

1. Create a dynamic API by calling the factory endpoint.
2. Save the returned `apiId` and `apiKey`.
3. Use the generated collection endpoints with `x-api-key`.
4. Optionally open Swagger docs for that generated API.

## Base URLs

The runtime base path comes from `API_BASE_URL` and `API_VERSION`.

- Default version in code: `v1`
- Current development base URL from `.env.development`: `http://localhost:9876`

So in local development, the factory endpoints are:

- `POST http://localhost:9876/api/v1/create-endpoint/:duration`
- `ALL  http://localhost:9876/api/v1/temp/:apiId/:collection`
- `GET  http://localhost:9876/api/v1/:apiId/docs/?apiKey=...`

Do not hardcode `v2`. The README mentions `v2`, but the current code defaults to `v1`.

## Auth You Need

There are 2 different auth layers.

### 1. Create API auth

To create a new API, the request passes through:

- `x-admin-key`
- `Authorization: Bearer <jwt>` or `access_token` cookie

Development fallback:

- If no JWT is sent and `NODE_ENV=development`, the backend accepts:
  - `x-user-id`
  - `x-session-id`

### 2. Generated API auth

All generated CRUD endpoints require:

- `x-api-key: <apiKey>`

Swagger docs can be opened with either:

- `x-api-key` header
- `?apiKey=<apiKey>` query param

## Response Shape

Most successful responses use this envelope:

```json
{
  "success": true,
  "message": "Human-readable message",
  "data": {}
}
```

Most errors use:

```json
{
  "success": false,
  "message": "Error message",
  "error": "Optional detail",
  "errors": [
    {
      "field": "fieldName",
      "message": "Validation error"
    }
  ]
}
```

Frontend clients should rely on:

- `success`
- HTTP status code
- `data`
- `errors` when present

Do not depend on emoji or exact `message` text.

## Step 1: Create a Dynamic API

### Endpoint

`POST /api/v1/create-endpoint/:duration`

### Allowed `duration` values

- `15-mins`
- `20-mins`
- `1-hour`
- `12-hours`
- `1-day`
- `7-days`
- `15-days`
- `30-days`
- `1-year`

### Example request

```bash
curl -X POST "http://localhost:9876/api/v1/create-endpoint/7-days" \
  -H "Content-Type: application/json" \
  -H "x-admin-key: YOUR_ADMIN_KEY" \
  -H "x-user-id: demo-user" \
  -H "x-session-id: demo-session" \
  -d '{
    "permission": "MCRUDQ",
    "soft_delete": true,
    "textIndexStrategy": "wildcard",
    "recordDefinitions": [
      {
        "record_name": "Product",
        "record_config": {
          "name": { "type": "String", "required": true, "min": 2, "max": 100 },
          "price": { "type": "Number", "required": true, "min": 0 },
          "category": { "type": "String", "enum": ["electronics", "fashion"] },
          "inStock": { "type": "Boolean", "default": true },
          "createdBy": { "type": "String" }
        }
      }
    ]
  }'
```

### Example success response

```json
{
  "success": true,
  "message": "Temporary multi-model API created! Store your API KEY safely.",
  "data": {
    "apiId": "a1b2c3d4e5f67890",
    "apiKey": "one-time-secret-key",
    "endpoints": [
      "http://localhost:9876/api/v1/temp/a1b2c3d4e5f67890/products"
    ],
    "collections": ["products"],
    "instanceDetails": {
      "dbUri": "mongodb://***:***@mongodb:27017/db_xxxx?authSource=admin",
      "dbName": "db_xxxx"
    },
    "expiresAt": "Wednesday, 26 Feb 2026, 15:30:00",
    "checkDocsAt": "http://localhost:9876/api/v1/a1b2c3d4e5f67890/docs/?apiKey=one-time-secret-key"
  }
}
```

Save `apiId` and `apiKey` immediately. The key is only returned at creation or regeneration time.

## Create Request Body Rules

### Top-level fields

- `permission`: required, one of `SCRUD`, `SCRUDQ`, `MCRUD`, `MCRUDQ`
- `soft_delete`: optional, default `false`
- `textIndexStrategy`: optional, `wildcard` or `explicit`
- `dbName`: optional
- `dbUri`: optional
- `recordDefinitions`: required, array of 1 to 20 models

### Permission meaning

- `SCRUD`: single model, CRUD, no advanced query features
- `SCRUDQ`: single model, CRUD, query features enabled
- `MCRUD`: multi model, CRUD, no advanced query features
- `MCRUDQ`: multi model, CRUD, query features enabled

Use a `Q` permission if the client needs filtering, sort, populate, select, or text search.

### Supported field types

- `String`
- `Number`
- `Boolean`
- `Date`
- `ObjectId`
- `Mixed`

### Supported field options

- `required`
- `unique`
- `ref`
- `enum`
- `default`
- `min`
- `max`
- `message`
- `select`
- `match`
- `searchable`

### Record name rules

- Must start with a letter
- Can contain letters, digits, and `_`
- Max length: 64
- Must be unique case-insensitively

### Schema depth and size limits

- Max nesting depth: 10
- `recordDefinitions` JSON size must stay within about `50 KB`

## Step 2: Use the Generated CRUD API

Each model becomes a pluralized collection route.

If `record_name` is `Product`, the collection route becomes:

`/api/v1/temp/:apiId/products`

Always send:

```http
x-api-key: <apiKey>
Content-Type: application/json
```

## CRUD Endpoints

For each collection:

- `POST   /temp/:apiId/:collection`
- `GET    /temp/:apiId/:collection`
- `POST   /temp/:apiId/:collection/bulk-create`
- `GET    /temp/:apiId/:collection/:id`
- `PATCH  /temp/:apiId/:collection/:id`
- `DELETE /temp/:apiId/:collection/:id`
- `GET    /temp/:apiId/:collection/advanced/count`

## Common Examples

### Create one record

```bash
curl -X POST "http://localhost:9876/api/v1/temp/API_ID/products" \
  -H "Content-Type: application/json" \
  -H "x-api-key: API_KEY" \
  -d '{
    "name": "Keyboard",
    "price": 99,
    "category": "electronics"
  }'
```

### List records

```bash
curl "http://localhost:9876/api/v1/temp/API_ID/products?page=1&limit=10" \
  -H "x-api-key: API_KEY"
```

### Get by id

```bash
curl "http://localhost:9876/api/v1/temp/API_ID/products/661f3d2f0f2e5e4ab1234567" \
  -H "x-api-key: API_KEY"
```

### Update

```bash
curl -X PATCH "http://localhost:9876/api/v1/temp/API_ID/products/661f3d2f0f2e5e4ab1234567" \
  -H "Content-Type: application/json" \
  -H "x-api-key: API_KEY" \
  -d '{
    "price": 89
  }'
```

### Delete

```bash
curl -X DELETE "http://localhost:9876/api/v1/temp/API_ID/products/661f3d2f0f2e5e4ab1234567" \
  -H "x-api-key: API_KEY"
```

### Bulk create

```bash
curl -X POST "http://localhost:9876/api/v1/temp/API_ID/products/bulk-create" \
  -H "Content-Type: application/json" \
  -H "x-api-key: API_KEY" \
  -d '[
    { "name": "Mouse", "price": 49, "category": "electronics" },
    { "name": "Monitor", "price": 199, "category": "electronics" }
  ]'
```

## Query Features

These only work with `SCRUDQ` or `MCRUDQ`.

### Pagination

- `page=1`
- `limit=10`

Notes:

- Default `limit` is `10`
- Max `limit` is `100`

### Sort

```text
?sort=-createdAt
?sort=price
?sort=category,-price
```

Only real schema fields are honored.

### Field selection

```text
?select=name,price,category
```

### Populate references

```text
?populate=author
?populate=author,comments
?populate=all
```

Only declared `ref` paths can be populated.

### Basic filtering

```text
?category=electronics
?inStock=true
?price=99
```

### Range and operator filters

```text
?price[gte]=100
?price[lte]=500
?price[gt]=50&price[lt]=300
?category[in]=electronics,fashion
?category[nin]=archived,test
```

### Full-text search

```text
?search=wireless keyboard
```

This only works when a text index exists for that model.

### Count endpoint

Use:

`GET /temp/:apiId/:collection/advanced/count`

It supports the same filter style and returns:

```json
{
  "success": true,
  "message": "Count retrieved!",
  "data": {
    "count": 42
  }
}
```

## Soft Delete Behavior

If the API was created with `soft_delete: true`:

- `DELETE` marks the record with `isDeleted: true`
- list and detail endpoints automatically exclude deleted records
- populated relations also exclude soft-deleted records
- clients cannot set `isDeleted` through `PATCH`

Frontend implication:

- A deleted record may disappear from list views immediately even though it still exists in MongoDB.

## Validation Notes

### Request validation happens twice

- Zod validates incoming payloads before DB access
- Mongoose validates on persistence/update

### Helpful client expectations

- Invalid body returns `400`
- Invalid Mongo ObjectId returns `400`
- Duplicate unique field returns `409`
- Expired API returns `404`
- Wrong API key returns `403`
- Missing API key returns `401`

### Bulk create limits

- Max 100 items per request
- Each document is capped at about `100 KB`

## Swagger Docs

Open:

`GET /api/v1/:apiId/docs/?apiKey=<apiKey>`

The docs are protected by the same generated API key.

Good use cases:

- Let frontend developers inspect schemas quickly
- Let an LLM discover fields and routes before generating requests

## API Key Regeneration

Endpoint:

`POST /api/v1/regenerate-api-key/:apiId`

This route requires authenticated user context. It is marked in code as not meant for production use yet.

Treat the new key as a full replacement for the old one.

## Rate Limits

- API creation: 5 requests per 15 minutes per IP
- Dynamic API usage: 60 requests per minute per IP

Frontend implication:

- Handle `429` gracefully with retry UI or backoff

## Recommended Frontend Integration Pattern

Persist these values after creation:

```ts
type DynamicApiSession = {
  apiId: string;
  apiKey: string;
  baseUrl: string;
  collections: string[];
  expiresAt: string;
};
```

Build collection URLs as:

```ts
const url = `${baseUrl}/api/v1/temp/${apiId}/${collection}`;
```

Attach headers on every request:

```ts
const headers = {
  "Content-Type": "application/json",
  "x-api-key": apiKey,
};
```

## Minimal fetch helper

```ts
async function callDynamicApi<T>(
  path: string,
  options: RequestInit = {},
): Promise<T> {
  const res = await fetch(path, {
    ...options,
    headers: {
      "Content-Type": "application/json",
      "x-api-key": apiKey,
      ...(options.headers || {}),
    },
  });

  const json = await res.json();

  if (!res.ok || !json.success) {
    throw new Error(json.message || "Request failed");
  }

  return json.data as T;
}
```

## LLM Agent Guidance

If an LLM is consuming this API, it should:

1. Read and store `apiId`, `apiKey`, `collections`, and `expiresAt`.
2. Use only the returned collection names instead of guessing pluralization.
3. Prefer Swagger docs before generating complex payloads.
4. Check whether permission includes `Q` before relying on filters, search, populate, or select.
5. Treat `apiKey` and `authenticatedDbUri` as secrets.
6. Handle `404` as either not found or expired API, depending on context.

## Important Current Implementation Notes

- Current runtime path version is `v1`, not `v2`.
- Query features are permission-gated by `Q`.
- The docs route is available only for APIs created with docs access enabled by the server flow.
- `bulk-create` exists even though it is currently hidden from generated Swagger.
- `/advanced/count` is part of the live API. A `/stats` route exists only on an unused subclass and should not be treated as public.
